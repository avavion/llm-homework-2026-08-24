## Базовый URL и формат обмена

- Локально: `http://localhost:8080` (порт из `API_PORT`, по умолчанию `8080`).
  Как поднять backend локально — отдельная инструкция
  [`frontend-backend-local-setup.md`](frontend-backend-local-setup.md).
- Тело запроса/ответа — `application/json`, кроме `POST
  /v1/product-drafts/recognize`, который принимает `multipart/form-data`.
- Даты и время — RFC 3339 / ISO 8601 с явным часовым поясом, например
  `"2026-09-01T00:00:00Z"`.
- Числа с плавающей точкой (`quantity`) сериализуются как JSON number.
- Поля, помеченные ниже как «опционально», при отсутствии значения либо не
  сериализуются вовсе (`omitempty`), либо приходят как `null`.

## Аутентификация и CORS

Backend использует **cookie-сессии**, а не Bearer-токены.

1. `POST /v1/auth/register` или `POST /v1/auth/login` — backend выставляет
   `Set-Cookie: session=...` (`HttpOnly`, `Secure`, `SameSite=Lax`, срок
   действия 30 дней).
2. Каждый следующий запрос к защищённым эндпоинтам браузер должен отправлять
   с этой cookie — используйте `fetch(url, { credentials: 'include' })` или
   `axios` с `withCredentials: true`. Без этого сервер ответит `401`.
3. `POST /v1/auth/logout` инвалидирует сессию на сервере и стирает cookie.
4. `GET /v1/auth/session` — способ проверить «залогинен ли я», удобно при
   загрузке SPA.

**CORS.** Backend разрешает запросы с credentials только с origin из
`FRONTEND_ORIGINS` (env-переменная backend, через запятую). По умолчанию
разрешены `http://localhost:5173` (Vite) и `http://localhost:3000`
(CRA/Next.js). Если ваш dev-сервер слушает другой порт/хост — попросите
добавить его в `.env` backend (см. инструкцию по запуску) или добавьте сами,
если поднимаете backend локально. Origin `*` с credentials не работает по
спецификации Fetch, поэтому запрос с незарегистрированного origin будет
заблокирован браузером ещё до попадания в код фронтенда (в Network tab это
выглядит как ошибка CORS, а не как `401`/`403`).

⚠️ **Важно:** используйте именно `http://localhost:<порт>` на обеих сторонах
(и backend, и frontend). `Secure`-cookie отправляется браузером по `http://`
только для origin `localhost`; для `127.0.0.1` или сетевого IP это может не
сработать — это известное ограничение, не баг конкретного эндпоинта.

## Формат ошибок

Все ошибки — JSON вида:

```json
{ "error": "human-readable message" }
```

Сообщение внутри `error` — служебное, для логов/дебага; не показывайте его
пользователю напрямую без локализации. Используемые коды состояния:

| Код | Значение |
| --- | --- |
| `400` | Невалидное тело запроса или бизнес-валидация (например, отсутствует обязательное поле, неверный `date_type`, порог уведомления < 60 минут). |
| `401` | Нет валидной сессии (нет cookie, cookie истекла/отозвана). |
| `404` | Ресурс не найден **или принадлежит другому аккаунту** — backend намеренно не различает эти два случая, чтобы не палить чужие ID. |
| `409` | Конфликт состояния (например, повторное `use`/`discard`, повторный `approve`/`reject` черновика). |
| `500` | Внутренняя ошибка backend. |

## Продукты — `internal/product`

Модель продукта, которую возвращает API (`PublicProduct`):

```json
{
  "id": "uuid",
  "name": "Milk",
  "date_type": "use_by",
  "expiry_date": "2026-09-01T00:00:00Z",
  "quantity": 1,
  "unit": "l",
  "product_group": "refrigerated_perishable",
  "storage_location": "fridge",
  "country_code": "DE",
  "alert_threshold_minutes": 4320,
  "status": "active",
  "completed_at": null,
  "created_at": "2026-08-26T18:15:04.06Z",
  "updated_at": "2026-08-26T18:15:04.06Z"
}
```

- `date_type` — `"use_by"` или `"best_before"`. Другие значения отклоняются с `400`.
- `status` — **только** жизненный цикл: `"active"` | `"used"` | `"discarded"`.
  ⚠️ См. раздел «Известные ограничения» — статусы `"attention"`/`"expired"`
  из продуктового описания **пока не возвращаются этим полем**.
- `quantity`, `unit`, `product_group`, `storage_location`, `country_code`,
  `alert_threshold_minutes`, `completed_at` — опциональны, отсутствуют
  (`omitempty`) или `null`, если не заданы.
- `alert_threshold_minutes` — минимум `60`; меньшее значение → `400`.

### `POST /v1/products`

Создать продукт. Требует сессию.

Тело запроса:

```json
{
  "name": "Milk",
  "date_type": "use_by",
  "expiry_date": "2026-09-01T00:00:00Z",
  "quantity": 1,
  "unit": "l",
  "product_group": "refrigerated_perishable",
  "storage_location": "fridge",
  "country_code": "DE",
  "alert_threshold_minutes": 4320
}
```

Обязательны только `name`, `date_type`, `expiry_date`. Остальные поля можно
опустить.

- `201` — тело `PublicProduct`.
- `400` — не хватает обязательного поля, неизвестный `date_type` или
  `alert_threshold_minutes < 60`.

### `GET /v1/products`

Список продуктов текущего аккаунта. `200` — JSON-массив `PublicProduct`
(может быть пустым `[]`).

### `GET /v1/products/:id`

Один продукт. `200` — `PublicProduct`; `404`, если не существует или
принадлежит другому аккаунту.

### `POST /v1/products/:id/use` и `POST /v1/products/:id/discard`

Завершить жизненный цикл продукта (тело запроса не требуется). `200` —
обновлённый `PublicProduct` со `status: "used"`/`"discarded"` и заполненным
`completed_at`. `404` — чужой/несуществующий продукт. `409` — продукт уже
был завершён (второй `use`/`discard` не создаёт второе завершение).

## Рецепты — `internal/recipe`

### `GET /v1/recipes`

Простые детерминированные подсказки по собственным активным продуктам
текущего аккаунта.

```json
[
  { "title": "Use up Milk", "product_ids": ["uuid"] },
  { "title": "Combine your fresh_produce items", "product_ids": ["uuid1", "uuid2"] }
]
```

`title` пока на английском и не локализован (см. известные ограничения).
Продукты со статусом `used`/`discarded` никогда не попадают в выдачу.
Продукт с подтверждённым регуляторным правилом и статусом `expired`
(`use_by` после срока) тоже исключается — но см. ниже: сегодня подтверждённых
правил нет, поэтому это исключение фактически не срабатывает ни для одной
страны.

## Черновики по фото — `internal/recognition`

⚠️ **Эта группа эндпоинтов сегодня нефункциональна для реального
распознавания** — см. «Известные ограничения». API-контракт стабилен и можно
верстать против него уже сейчас, но `POST /recognize` в текущем деплое всегда
вернёт `400` с `ErrRecognitionUnavailable`, потому что OCR/LLM-провайдеры не
подключены (заглушки). Ручной ввод через `/v1/products` — единственный
рабочий путь добавления продукта сегодня.

Модель черновика:

```json
{
  "id": "uuid",
  "status": "pending",
  "raw_text": "распознанный OCR-текст",
  "fields": {
    "Name": "Milk",
    "DateType": "use_by",
    "ExpiryDate": "2026-09-01T00:00:00Z",
    "Quantity": 1,
    "Unit": "l",
    "ProductGroup": null,
    "StorageLocation": null,
    "CountryCode": null
  },
  "approved_product_id": null
}
```

⚠️ Обратите внимание: вложенный объект `fields` сериализуется **с полями в
PascalCase** (`Name`, `DateType`, ...), а не в `snake_case`, как весь
остальной API. Это несогласованность в текущей реализации (см. известные
ограничения) — не опечатка в этом документе.

- `status` — `"pending"` | `"approved"` | `"rejected"`.
- `approved_product_id` — заполняется после `approve`.

### `POST /v1/product-drafts/recognize`

`multipart/form-data` с полями:
- `image` (file, обязателен) — фото упаковки, максимум 10 МиБ.
- `locale` (string, опционально) — подсказка языка для LLM-этапа.

- `201` — созданный черновик (`status: "pending"`), продукт **не создаётся**.
- `400` — нет файла `image`, файл пустой/слишком большой, либо
  `ErrRecognitionUnavailable` (см. предупреждение выше — сегодня всегда этот
  случай в реальном окружении).

### `GET /v1/product-drafts/:id`

Перечитать черновик (например, после перезагрузки страницы, если черновик из
`recognize` был потерян). `200` — тот же формат, что и `recognize`. `404` —
чужой/несуществующий черновик.

### `POST /v1/product-drafts/:id/approve`

Тело — те же поля, что и у `POST /v1/products` (`name`, `date_type`,
`expiry_date` обязательны; остальное опционально). Frontend обязан прислать
**полные отредактированные пользователем данные** — backend не подставляет
их сам из сохранённого черновика.

- `201` — тело `PublicProduct` (тот же формат, что у `/v1/products`,
  `snake_case`, без несогласованности из `fields` выше).
- `400` — невалидные отредактированные поля (та же валидация, что у
  создания продукта).
- `404` — чужой/несуществующий черновик.
- `409` — черновик уже был `approve`d или `reject`ed ранее.

### `POST /v1/product-drafts/:id/reject`

Тело не требуется. `204` без тела — продукт не создаётся. `404`/`409` — как
выше.

## Аутентификация — `internal/auth` (уже задокументировано в BE-003, кратко)

| Метод и путь | Тело | Успех | Ошибки |
| --- | --- | --- | --- |
| `POST /v1/auth/register` | `{"email","password"}` | `201 {"id","email"}` | `400` невалидные данные, `409` email занят |
| `POST /v1/auth/login` | `{"email","password"}` | `200 {"id","email"}` + `Set-Cookie` | `401` неверные данные |
| `POST /v1/auth/logout` | — | `204` | — |
| `GET /v1/auth/session` | — | `200 {"id","email"}` | `401` нет сессии |

`register`/`login` **строго** отклоняют JSON с неизвестными полями или
лишними данными после объекта (`400`). Остальные эндпоинты (`products`,
`product-drafts`) этого не делают — присланные лишние поля просто
игнорируются. Это расхождение в строгости валидации между модулями, а не
специально спроектированное поведение.

## Известные ограничения и не закрытые баги

Прочитайте перед интеграцией — часть перечисленного выглядит как баг, но
является осознанно отложенным решением; часть — реальный технический долг:

1. **Нет вычисляемого статуса `attention`/`expired`.** Поле `status`
   продукта отдаёт только жизненный цикл (`active`/`used`/`discarded`).
   Логика вычисления регуляторного статуса есть (`internal/regulation`,
   `internal/recipe`), но никакой эндпоинт пока не отдаёт её наружу для
   отображения в карточке продукта. Если фронтенду нужен бейдж «просрочено»/
   «требует внимания» — этого сегодня нет в API, нужно отдельно запрашивать
   у backend.
2. **Реестр регуляторных правил пуст.** Все строки в
   [`shared/docs/regulatory-date-rules.md`](regulatory-date-rules.md) имеют
   статус `research_required` — ни для одной страны нет подтверждённого
   правила. Следствие: e-mail-уведомления **никогда не отправляются** и
   `GET /v1/recipes` никогда не исключает продукт по сроку — это ожидаемо, а
   не баг рассылки/задачи планировщика.
3. **OCR/LLM не подключены.** `POST /v1/product-drafts/recognize` в текущем
   окружении всегда возвращает `400` — используются заглушки
   (`UnconfiguredOCRClient`/`UnconfiguredLLMClient`). UI для фото можно
   верстать заранее, но End-to-End сценарий распознавания не заработает,
   пока backend не подключит реального провайдера.
4. **`fields` в ответах `product-drafts` — не `snake_case`.** См. пример
   выше; это несогласованность именования полей в текущей реализации.
5. **Локализация текстов API отсутствует.** Сообщения об ошибках и заголовки
   рецептов — на английском/техническом языке, не предназначены для показа
   пользователю без перевода на фронтенде.
6. **Нет rate limiting и явных лимитов размера тела запроса** (кроме 10 МиБ
   на фото и 1 МиБ на `/v1/auth/*`). Не полагайтесь на сервер в защите от
   некорректно больших запросов на остальных эндпоинтах.
7. **Формальная QA-приёмка (`BE-007`) не проводилась.** Есть только
   unit/интеграционные тесты разработчика и один раунд ручного smoke-теста.
8. **Секьюрити-обзор не проводился** (`security-review` не запускался на
   этом коде). Не считайте эндпоинты проверенными на распространённые
   уязвимости сверх того, что покрывают тесты.
