# Workflow: независимая проверка готовности релиза

Эта процедура применяется к каждой следующей версии Food Expiry. Исполнитель
проверки не должен быть автором проверяемых изменений и не меняет код во время
прогона: он фиксирует наблюдения в отдельном отчёте.

## 1. Входные условия

Запускайте процедуру из корня репозитория. Перед началом рабочая ветка должна
быть чистой: сохраните или уберите незакоммиченные изменения, затем проверьте
её состояние.

```sh
git status --short
docker compose version
node --version
npm --version
go version
```

Требуются Docker с плагином Docker Compose, Node.js и npm, а также Go 1.25
(версия зафиксирована в [`backend/go.mod`](backend/go.mod)). Должны быть
свободны порты `8080` (API) и `4173` (frontend). Если нужны другие порты,
выберите две свободные и везде ниже подставьте их вместо значений по умолчанию:

```sh
API_PORT=8090 FRONTEND_PORT=4174 make up
```

Нельзя объявлять релиз проверенным, если Docker, Go, npm, доступ к Docker daemon
или нужные порты отсутствуют: это статус `blocked`, а не успешный прогон.

## 2. Подготовка окружения

Поднимите production-подобное локальное окружение:

```sh
make up
```

`make up` выполняет `npm ci` и production-сборку frontend, собирает Go API,
поднимает API и PostgreSQL через [`backend/docker-compose.yml`](backend/docker-compose.yml),
применяет миграции и запускает Vite Preview. После команды выполните проверки
доступности:

```sh
curl --fail --show-error http://localhost:8080/healthz
curl --fail --show-error --output /dev/null http://localhost:4173/
```

Ожидаются `200 OK`, JSON `{"status":"ok"}` от `/healthz` и успешный HTTP-ответ
главной страницы frontend. Если использовались другие порты, замените URL в
командах. После завершения проверки остановите окружение командой `make down`;
она останавливает API и PostgreSQL, не удаляя том PostgreSQL.

## 3. Автоматические проверки

Проведите каждый прогон отдельно и сохраните в отчёт точную команду, код
завершения и существенный вывод:

```sh
cd backend && make test
cd backend && make test-integration

cd frontend && npm run lint
cd frontend && npm test
cd frontend && npm run test:e2e
```

`backend make test` — unit-тесты Go. `backend make test-integration` использует
Docker Compose и запускает auth-интеграционный тест с отдельным compose project;
Docker обязателен. Frontend-проверки используют зависимости из
`frontend/package-lock.json`; если `make up` не запускался в этой рабочей копии,
перед ними выполните `cd frontend && npm ci`. `npm run test:e2e` запускает
Playwright и его собственный Vite dev-server на `127.0.0.1:4173`; для него нужны
установленные браузеры Playwright. Он использует frontend mock API, поэтому не
заменяет проверку реального API из раздела 2.

## 4. Независимый агент-ломатель

После автоматических проверок отдельный агент проводит негативную проверку
работающего API и браузерного клиента. Он использует два новых аккаунта,
сохранённые cookie-сессии и созданные в ходе проверки UUID; не использует чужие
реальные данные. Защищённые маршруты API и ожидаемые коды описаны в
[`shared/docs/backend-api-reference.md`](shared/docs/backend-api-reference.md).

Минимальный набор сценариев:

| № | Сценарий | Ожидаемый безопасный результат |
| --- | --- | --- |
| 1 | `POST /v1/products` без cookie-сессии | `401`; продукт не создан. |
| 2 | Невалидный JSON и пустое тело в `POST /v1/auth/register` | `400`, JSON-ошибка, без паники API. |
| 3 | Пустой `{}` и повреждённый JSON в `POST /v1/products` авторизованного пользователя | `400`; список продуктов не изменён. |
| 4 | Создание продукта с неверным `date_type` или неразбираемой `expiry_date` | `400`; продукт не создан. |
| 5 | Граница `alert_threshold_minutes`: `59` и `60` в создании продукта или `PUT /v1/notification-settings` | `59` отклонён с `400`; `60` принимается, если остальные поля валидны. |
| 6 | `GET /v1/products/not-a-uuid` и завершение продукта с несуществующим UUID | `404`; API продолжает отвечать на `/healthz`. |
| 7 | Два последовательных вызова `POST /v1/products/:id/use` либо `discard` для одного продукта | первый завершает продукт, повтор возвращает `409`; терминальное состояние не меняется. |
| 8 | Два параллельных завершающих вызова (`use` и/или `discard`) к одному активному продукту | не более одного успешного перехода; остальные ответы фиксируются, а итоговый продукт имеет одно терминальное состояние. |
| 9 | Второй аккаунт запрашивает, завершает или читает UUID продукта первого | `404` для каждого защищённого доступа; данные первого аккаунта не раскрыты. |
| 10 | Повторная регистрация одного e-mail и вход с неверным паролем | соответственно `409` и `401`; действующая сессия другого аккаунта не затронута. |
| 11 | `POST /v1/product-drafts/recognize` без multipart-поля `image` и с пустым файлом | `400`; API не падает. |
| 12 | Вызов `approve` или `reject` для несуществующего/чужого UUID черновика, а также повторное решение существующего черновика, если в среде настроен провайдер | `404` для отсутствующего/чужого и `409` для повторного решения; созданный продукт не дублируется. |
| 13 | Имя продукта, содержащее `<img src=x onerror=alert(1)>`, через форму ручного добавления | строка отображается как текст; в таблице не появляется исполняемый `img`-элемент. |

Сценарии 12, требующие создания черновика, могут быть недоступны в стандартной
локальной конфигурации: без `RECOGNITION_PROVIDER` endpoint распознавания
намеренно отвечает `400`. Это ограничение среды следует записать в отчёт и не
выдавать за пройденную проверку. Все остальные сценарии проверяются на реально
поднятом API; для ручной проверки используйте только существующие маршруты из
таблицы, не придумывая тестовые endpoint’ы.

## 5. Фиксация результата

Создайте новый, не перезаписывающий прошлые записи файл
`docs/release-readiness-YYYY-MM-DD.md`. В нём должны быть:

1. проверяемый commit (`git rev-parse HEAD`) и дата;
2. фактические команды из разделов 1–4, их коды завершения и результаты;
3. результаты каждого негативного сценария, включая созданные только для теста
   ID без сессионных cookie и персональных данных;
4. находки с уровнем серьёзности, шагами воспроизведения и наблюдаемым
   результатом;
5. ограничения окружения: недоступный Docker/Go/npm/Playwright, занятый порт,
   отсутствие браузера или `RECOGNITION_PROVIDER`;
6. итоговый статус и следующие шаги: владелец исправления, повторная команда и
   условие перепроверки.

## 6. Статусы решения

- `passed` — все обязательные команды и доступность из разделов 2–3 успешны,
  все применимые негативные сценарии дали ожидаемый безопасный результат, а
  непроверяемые возможности явно перечислены как ограничения без критичного
  риска для релиза.
- `changes_required` — среда работоспособна, но тест, health-check или
  негативный сценарий обнаружил дефект, регрессию или расхождение с контрактом.
  Релиз не выпускается до исправления и повторного прогона.
- `blocked` — воспроизводимый прогон невозможен из-за отсутствующего runtime,
  Docker daemon, занятых портов, зависимостей или другого внешнего ограничения.
  Укажите причину и команду, которую нужно повторить после устранения блока.

## 7. Повторный запуск

Для следующей версии начните с чистой ветки и выполните последовательность:

```sh
git status --short
make up
curl --fail --show-error http://localhost:8080/healthz
curl --fail --show-error --output /dev/null http://localhost:4173/
cd backend && make test
cd backend && make test-integration
cd frontend && npm run lint
cd frontend && npm test
cd frontend && npm run test:e2e
```

Затем передайте работающий URL и результаты независимому агенту-ломателю из
раздела 4, создайте новый отчёт из раздела 5 и завершите локальный запуск:

```sh
make down
```
