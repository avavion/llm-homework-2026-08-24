# Design Requirements — Editorial Pantry

## 1. Цель и границы

Редизайн делает приложение для учёта срока годности визуально тёплым и редакционным, сохраняя все текущие пользовательские сценарии: авторизация, инвентарь, ручное и фото-добавление, черновики, жизненный цикл продукта, рецепты и настройки. Это не изменение API или бизнес-правил.

Визуальная основа — **Editorial Pantry**: спокойный кремовый холст, выразительная журнальная типографика в заголовках и компактный функциональный интерфейс для данных. Каждый экран имеет одно главное действие; статус продукта никогда не передаётся только цветом.

## 2. Дизайн-токены

| Группа | Токен | Значение | Использование |
| --- | --- | --- | --- |
| Canvas | `--canvas` | `#FFF8F0` | Основной фон |
| Surface | `--surface` | `#FFFFFF` | Карточки, поля, диалоги |
| Ink | `--ink` | `#2A211B` | Основной текст, иконки |
| Muted | `--muted` | `#6D6259` | Вторичный текст; только с проверенным AA-контрастом |
| Brand | `--brand` | `#C94B35` | Основная кнопка, активная навигация |
| Brand dark | `--brand-strong` | `#9E3525` | Hover/pressed |
| Olive | `--olive` | `#66704A` | Успешные и спокойные статусы |
| Attention | `--amber` | `#A65A00` | Требует внимания |
| Danger | `--danger` | `#B42318` | Просрочен, удаление |
| Focus | `--focus` | `#2C5C8A` | Видимый focus-ring |

- Заголовки: `Playfair Display`, 600–700. UI и текст: `DM Sans`, 400–700. Если веб-шрифты недоступны, используются системные serif/sans fallback.
- Размеры: 12, 14, 16, 20, 24, 32, 40, 56px; основной текст не менее 16px.
- Радиусы: 12px для controls, 20px для card/sheet, 28px только для hero-элементов.
- Тени: одна шкала мягких теней для floating/card, без glassmorphism и тяжёлых декоративных эффектов.
- Движение: 160ms hover/pressed, 220ms sheet/dialog; только `opacity` и `transform`; при `prefers-reduced-motion` — без переходов.

## 3. Структура экранов

| Экран | Композиция и главный акцент |
| --- | --- |
| Вход / регистрация | Desktop split-screen: food-story panel и форма. Форма занимает 420–480px, имеет брендинг, заголовок, переключатель вход/регистрация, видимые labels и одно CTA. Используется оригинальная графика/цветовой фон; композиция может следовать указанному Behance-референсу. |
| Инвентарь | Редакционный header с датой и коротким фокусным сообщением; далее priority-card для 1–3 срочных продуктов, фильтры и плотный data-list. Primary CTA «Добавить продукт» постоянно доступен. |
| Карточка продукта | Название, дата с типом `use by` / `best before`, место хранения, статус и lifecycle-действия. Иконка + текст + цвет фиксируют статус. |
| Добавление вручную | Чистая форма в surface-card: обязательные поля в первом блоке, хранение и количество в раскрываемых деталях. Под датой — safety-explainer. |
| Добавление по фото / черновик | Большая upload-card с объяснением; прогресс во время распознавания; затем те же редактируемые поля с заметной меткой «Черновик» и действиями approve/reject. |
| Детали продукта | Крупное название и статусный блок, затем факты; действия «Использован»/«Выброшен» визуально разделены. |
| Рецепты | Редакционная сетка карточек на широких экранах; на карточке явно указан продукт-основание и его дата. Нельзя показывать просроченный `use by` как ингредиент. |
| Настройки | Две независимые группы: профиль/страна и пороги e-mail-уведомлений. Каждая группа имеет отдельное сохранение и feedback. |

## 4. Layout и адаптивность

| Ширина | Стратегия |
| --- | --- |
| 320–639px | Один столбец, 16px gutters, mobile bottom-nav, основной CTA шириной контейнера; интерактивные зоны минимум 44×44px. |
| 640–1023px | 24px gutters, верхняя навигация, карточки рецептов в две колонки, форма в одну или две колонки по доступной ширине. |
| 1024–1279px | Узкая левая rail-навигация; основная зона и priority-column используют CSS grid. |
| **1280px и шире** | Внешняя оболочка приложения (включая rail) растягивается на доступную ширину viewport: `width: min(100% - 64px, 1600px)`; при 1280px она не уже 1216px. Rail — 232px, main — `minmax(0, 1fr)`, supporting column — 300–360px. Основная область не получает отдельный узкий `max-width: 1240px`. |

На любых ширинах исключены горизонтальный scroll, обрезание подписей, перекрытие keyboard-focus фиксированной навигацией и reliance на hover. На 1280px data-list остаётся таблицеподобным, а не сворачивается преждевременно в карточки.

## 5. Компоненты и состояния

| Компонент | Default / interaction | Loading / disabled | Error / special |
| --- | --- | --- | --- |
| Button | Brand fill; hover/pressed меняет тон без сдвига layout | `disabled`, spinner, copy «Сохраняем…» | destructive использует danger и требует подтверждения |
| Input/select | Видимый label, helper, 44px min-height, focus-ring | Заблокированный control семантически disabled | `aria-invalid`, inline error, связан через `aria-describedby` |
| Form | Валидация on blur и при submit; password manager и paste разрешены | Submit не допускает дубль-запрос | При нескольких ошибках — focusable error-summary с якорями полей |
| Product row/card | Информация → дата → статус → действие | Skeleton повторяет конечную геометрию | Empty state сообщает причину и даёт одно релевантное действие |
| Status | Иконка, text-label, контрастный tone | — | Не опирается только на зелёный/красный |
| Dialog/sheet | Ясный title, последствия действия, close-control | Primary CTA блокируется на mutation | `role=dialog`, `aria-modal`, focus trap, Escape, возврат фокуса trigger |
| Toast/alert | `aria-live=polite`, не крадёт фокус | — | Понятный recovery action: retry/edit; error не скрывает введённые данные |

## 6. Доступность и качество

- Семантика: skip-link, `<header>`, `<nav>`, `<main>`, один `<h1>` на route, native button/input до кастомных элементов.
- Контраст обычного текста — не менее 4.5:1; границы и meaningful icons — не менее 3:1. Дизайн проверяется независимо в светлой и тёмной схеме, если тёмная будет добавлена.
- Keyboard: логичный Tab-order, Enter/Space для controls, Escape для dialog/sheet, после смены маршрута focus получает `<main>`/`h1`.
- Производительность: reserve media space, `loading=lazy` для неблокирующих изображений, route-level lazy loading при выносе экранов, без новых тяжёлых UI-библиотек.

## 7. Критерии приёмки

- [ ] Все существующие маршруты и API-сценарии работают без изменения контрактов.
- [ ] Login и register используют split-layout в утверждённой editorial-композиции и собственные assets.
- [ ] На 375, 768, **1280** и 1440px нет горизонтального overflow; при 1280px внешняя оболочка не уже 1216px и основная область не ограничена отдельным `max-width: 1240px`.
- [ ] Проверены hover, focus, active, disabled, loading, error и empty состояния.
- [ ] Пройдены keyboard smoke-test, контраст WCAG AA и Playwright visual checks.
- [ ] У пользователя есть понятный следующий шаг на каждом пустом и ошибочном экране.
