# Отчёт независимого негативного тестирования

**Дата:** 2026-08-29
**Проверяемый commit:** `2d1c63c869563712c64ca4fb8e4244bc6f9a2737`
**Объект:** локальный backend Food Expiry, поднятый напрямую через
`docker compose up -d --build api` в `backend/` (без frontend), API —
`http://localhost:8080`. Docker daemon пришлось запускать вручную перед
прогоном (`open -a Docker`), после чего API и PostgreSQL поднялись штатно,
`GET /healthz` отвечал `{"status":"ok"}` на протяжении всего прогона.
**Цель:** намеренно сломать сервис — пустые/кривые данные, границы
диапазонов, повторные и параллельные запросы, неверный порядок вызовов,
очень длинные строки, отрицательные/дробные суммы, чужие идентификаторы.

## Итог

В отличие от прогона 2026-08-28 (заблокирован отсутствием Go/Docker), в этот
раз сервис был полностью доступен. Выполнено 66 отдельных запросов по 18
сценариям. Аутентификация, изоляция аккаунтов (IDOR) и все проверенные гонки
(race conditions) выдержали атаку без единого пробоя. При этом найдено
**два способа получить необработанную `500`-ошибку или бесконтрольно раздуть
БД** и несколько расхождений с задокументированным контрактом API. Падений
процесса, зависаний или потери доступности `/healthz` не зафиксировано ни в
одном сценарии.

## Найденное, по опасности

| Уровень | Находка | Доказательство | Влияние |
|---|---|---|---|
| P1 / высокий | `POST /v1/auth/register` с email ~1 МБ (в пределах 1 MiB лимита тела) возвращает необработанный `500 Internal Server Error`, а не `400` | `internal/auth/service.go:26,67` — `Register()` проверяет только непустоту email/пароля, длину не ограничивает; запрос с полем `email` из ~1 048 400 символов дал `HTTP 500 {"error":"internal server error"}`; ошибка нигде не залогирована в stdout API-контейнера | Любой аноним может штатно получать `500` с публичного эндпоинта; отсутствие серверного лога по 500-кам мешает расследованию инцидентов. |
| P1 / высокий | Нет ограничения размера тела на `/v1/products` (в отличие от `/v1/auth/*`, где лимит 1 MiB, и `/recognize`, где лимит 10 MiB на файл) | `POST /v1/products` с полем `name` из 5 000 000 символов создан штатно, `201`, вернулся в `GET /v1/products` без проблем | Авторизованный пользователь (регистрация тривиальна) может копить в БД сколь угодно большие записи — дешёвый вектор исчерпания диска/памяти; в сочетании с отсутствием rate limiting это уже названо известным ограничением в `shared/docs/backend-api-reference.md`, п. 6, и здесь подтверждено практикой. |
| P2 / средний | `quantity` продукта принимает отрицательные и физически бессмысленные значения без валидации | `POST /v1/products` с `quantity: -5` → `201`; с `quantity: 1e308` → `201`, значение сохранено как есть | Ломает целостность данных инвентаря («-5 литров молока»); любая будущая логика агрегации/рецептов/уведомлений унаследует мусорные значения. |
| P2 / средний | `POST /v1/auth/register` не выставляет `Set-Cookie`, хотя `backend-api-reference.md` обещает cookie-сессию после регистрации так же, как после `login` | `internal/auth/http.go`, `registerHandler` (строки 41–59): вызова `http.SetCookie` нет, в отличие от `loginHandler` (строка 79); подтверждено `curl -v` — `Set-Cookie` в ответе `register` отсутствует, `GET /v1/auth/session` сразу после регистрации даёт `401` | Контракт API нарушен. Текущий frontend это маскирует (`frontend/src/app.tsx:131` после успешной регистрации явно редиректит на `/login`, не полагаясь на авто-логин), но любой другой клиент, написанный строго по документации, получит "пользователь как будто не залогинен" сразу после регистрации. |
| P2 / средний | Email не проверяется на формат вообще | `POST /v1/auth/register` с `email: "not-an-email"` и с email-подобной SQLi-строкой (`a@b.com' OR 1=1;--`) — оба раза `201`, значение сохранено как есть (в нижнем регистре) | Инъекции не происходит (параметризованные запросы), но при появлении email-уведомлений (сейчас не работают, см. известное ограничение реестра регуляторных правил) отправка гарантированно будет падать на мусорных адресах. |
| P3 / низкий | Нет минимальной длины/сложности пароля | `POST /v1/auth/register` с `password: "a"` → `201` | Слабая политика паролей для приложения, хранящего персональные данные пользователя. |
| P3 / низкий | `expiry_date = "0001-01-01T00:00:00Z"` не может быть сохранена — валидатор путает её с «дата не передана» | `POST /v1/products` с этой датой → `400 {"error":"name, date type, and date are required"}`, хотя `name` и `date_type` присланы корректно | Значение совпадает с zero-value `time.Time` в Go; реализационная деталь протекает в публичный контракт API. |
| P4 / косметический | Непоследовательная проверка обязательности `name`: пустая строка отклоняется, строка из пробелов — нет | `name: ""` → `400`; `name: "    "` → `201` | Минорная несогласованность валидации, не влияет на безопасность. |
| P4 / косметический | `Content-Type` не проверяется на `/v1/products` | Запрос с `Content-Type: text/plain` и валидным JSON-телом принят, `201` | Расходится и с документированным `application/json`-контрактом, и со строгостью `/v1/auth/*`, который такие тела отклоняет. |

## Выполненные негативные сценарии

Все запросы — `curl` на `http://localhost:8080`; параллельные сценарии — через
фоновые `curl`-процессы с `wait`. Использовались только тестовые аккаунты
(`userA@test.com`, `userB@test.com`, `racer@test.com` и другие созданные в
ходе прогона), без реальных персональных данных.

| № | Сценарий | Запрос | Фактический результат |
|---:|---|---|---|
| 1 | Пустая/повреждённая регистрация | `POST /v1/auth/register` c `{}`, с пустыми строками, с оборванным JSON | `400` во всех случаях, без паники. |
| 2 | SQLi-подобный и невалидный по формату email | `POST /v1/auth/register` c `a@b.com' OR 1=1;--` и `not-an-email` | `201` — инъекции нет, но формат не проверяется (находка P2). |
| 3 | Пароль в 1 символ / пароль >72 байт (лимит bcrypt) | `POST /v1/auth/register` | Оба раза `201`; логин обрезанным до 72 байт паролем вместо полного дал `401` — усечения bcrypt для обхода нет. |
| 4 | Регистрация с одинаковым email в разном регистре | Два `POST /v1/auth/register` | Второй — `409`, дедупликация регистронезависима. |
| 5 | 10 параллельных `register` с одним и тем же email | 10 фоновых `curl` одновременно | Ровно один `201`, остальные девять — `409`; дублей аккаунта не возникло. |
| 6 | Лишние/неизвестные поля и мусор после JSON-объекта в `register`/`login` | `{"email":...,"password":...,"isAdmin":true}`, `{...}{"garbage":1}` | `400` в обоих случаях — строгий парсинг соблюдён, как и обещано в доке. |
| 7 | Доступ к защищённым маршрутам без cookie, с подделанной cookie, после `logout` | `GET /v1/products`, `GET /v1/auth/session` с `session=totally-fake-token-value`, повтор старой cookie после `logout` | Везде `401`; `logout` инвалидирует сессию на сервере — старая cookie перестаёт работать сразу, а не только очищается на клиенте. |
| 8 | Отсутствие `Set-Cookie` у `register` | `POST /v1/auth/register` → `curl -v` | Подтверждено: `Set-Cookie` нет (находка P2), у `login` — есть, с `HttpOnly; Secure; SameSite=Lax`. |
| 9 | Отрицательное / гигантское / `NaN` количество | `quantity: -5`, `quantity: 1e308`, `quantity: NaN` | `-5` и `1e308` — `201` (находка P2); `NaN` как невалидный JSON-литерал — `400`. |
| 10 | Границы `alert_threshold_minutes` при создании продукта и в `notification-settings` | `59` → `400`, `60` → `201`/`200`, отрицательные и дробные (`61.9`) → `400` | Строго по контракту на всех проверенных путях. |
| 11 | Невалидный `date_type`, даты без таймзоны, только дата без времени, экстремальные годы (`9999`, `0001`) | `POST /v1/products` | `date_type` неизвестного значения и даты без таймзоны — `400`; год `9999` — `201`; год `0001` — ошибочно `400` "поле не передано" (находка P3). |
| 12 | IDOR: userB читает/использует продукт userA | `GET /v1/products/{id}`, `POST /v1/products/{id}/use` с чужой cookie | `404` в обоих случаях — чужой ID не палится, доступ не получен. |
| 13 | Повторный и параллельный `use`/`discard` одного продукта | Один `use`, затем `discard`; затем 20 параллельных `use` на новый продукт | Второй вызов (`discard` после `use`) — `409`; из 20 параллельных — ровно один `200`, 19 — `409`. Гонки на двойное завершение нет. |
| 14 | Не-UUID и SQLi/path-traversal в `:id` | `GET /v1/products/not-a-uuid`, `.../1' OR '1'='1`, `.../../../etc/passwd` | `404` везде, инъекции и обхода пути нет. |
| 15 | Экстремально длинное имя продукта (5 000 000 символов) | `POST /v1/products` | `201`, продукт создан и возвращается в списке (находка P1 — нет лимита тела). |
| 16 | XSS-пейлоад в имени продукта | `name: "<script>alert(1)</script>"` | `201`, значение в JSON-ответе корректно экранировано (`<script>`) — сам API не уязвим. |
| 17 | Пустая строка / строка из пробелов в `name` | `name: ""` → `400`; `name: "    "` → `201` | Несогласованность валидации (находка P4). |
| 18 | Глубоко вложенный JSON (до 200 000 уровней) как `product_group` | `POST /v1/products` с телом ~400 КБ | `400` (ожидаемая ошибка типа поля), `/healthz` после запроса — по-прежнему `200`; JSON-бомба сервис не уронила. |
| 19 | Профиль и notification-settings: невалидный `country_code`, неподдерживаемый `language`, неизвестная `product_group` | `PUT /v1/profile`, `PUT /v1/notification-settings` | `400` во всех случаях, включая `country_code` длиной >2 и с цифрами. |
| 20 | Recognition-эндпоинт: без файла, пустой файл, файл >10 МиБ, не-картинка, запрос к несуществующему draft | `POST /v1/product-drafts/recognize`, `GET/approve /v1/product-drafts/{id}` | `400`/`404` во всех случаях, падений нет; реальное распознавание недоступно (`RECOGNITION_PROVIDER` не задан) — соответствует известному ограничению из `backend-api-reference.md`. |
| 21 | CORS с недопустимым `Origin` | `OPTIONS`/`GET` с `Origin: http://evil.example.com` | Preflight отдаёт заголовки CORS без `Access-Control-Allow-Origin` для чужого origin; фактический запрос сервер не блокирует сам — это ожидаемо (CORS — браузерный механизм, реальная защита от CSRF — `SameSite=Lax`), отдельной находкой не считается. |
| 22 | Очень длинный email при регистрации (~1 МБ, под лимитом тела в 1 MiB) | `POST /v1/auth/register` | `500 Internal Server Error` вместо `400` (находка P1); тело ровно за лимитом 1 MiB — корректный `400` от `http.MaxBytesReader`. |

## Что устояло без пробоя

- Изоляция аккаунтов (IDOR) — чтение, `use`, `discard` чужих продуктов всегда `404`.
- Гонки: параллельная регистрация одного email и параллельный `use` одного продукта — ровно один успех, без дублей и без двойного завершения жизненного цикла.
- Инвалидация сессии на `logout` — серверная, а не только очистка cookie на клиенте.
- SQL-инъекции и path traversal в email, пароле и `:id` пути — не проходят.
- JSON-бомбы (глубокая вложенность), массив вместо объекта, оборванный JSON — стабильный `400`, без зависаний и падений.
- Строгий парсинг `register`/`login` (лишние поля, мусор после объекта) — соответствует документации.
- Усечение пароля в bcrypt (>72 байт) не позволяет войти укороченной версией пароля.
- Recognition-эндпоинт корректно обрабатывает пустой/оversized/не-картиночный файл без падений.

## Условия для повторного запуска

1. Перед прогоном запустить Docker Desktop (`docker info` должен отвечать) и
   поднять только backend: `cd backend && docker compose up -d --build api`,
   затем применить миграции (`docker compose exec -T api /migrate ...` — см.
   `scripts/local-up.sh`).
2. Приоритет для повторной проверки — находки P1: подтвердить фикс лимита
   длины email/пароля в `Register()` и добавление лимита тела для
   `/v1/products` (и других non-auth эндпоинтов), затем повторить сценарии 15
   и 22.
3. Сценарии с реальным распознаванием (`approve`/`reject` черновика) остаются
   недоступны без `RECOGNITION_PROVIDER=mock` — при следующем прогоне стоит
   поднять окружение с этой переменной, чтобы закрыть сценарий 12 из
   `WORKFLOW.md`, который в этом прогоне не выполнялся отдельно от recognition.
