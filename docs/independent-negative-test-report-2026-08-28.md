# Отчёт независимого негативного тестирования

**Дата:** 2026-08-28  
**Объект:** локальный запуск Food Expiry (`make up`, API `http://127.0.0.1:8080`)  
**Цель:** попытаться намеренно сломать сервис нестандартными и недоверенными входными данными.

## Итог

Подтверждён один критический блокер окружения: локальный сервис не запускается.
Команда `make up` успешно установила зависимости и собрала frontend, но остановилась
на backend-сборке с ошибкой:

```text
/bin/sh: go: command not found
make[1]: *** [backend-build] Error 127
make: *** [up] Error 2
```

Поэтому API не слушает `127.0.0.1:8080`. Найти прикладную ошибку, обойти
валидацию или подтвердить изоляцию аккаунтов невозможно: все запросы были
отклонены сетевым уровнем до выполнения обработчика.

## Найденное, по опасности

| Уровень | Находка | Доказательство | Влияние |
|---|---|---|---|
| P1 / критический | Локальный production-запуск неработоспособен без Go toolchain | `make up` завершился с `go: command not found` | Нельзя запустить API, миграции и полноценную проверку сервиса. |

Других находок не зафиксировано. Это **не** означает, что прикладной API
устойчив: он не был доступен для исполнения сценариев.

## Выполненные негативные сценарии

`http://127.0.0.1:8080` с таймаутом 3 секунды. Фактический результат каждого:
`http=000`, `curl: (7) Failed to connect ... Couldn't connect to server`.

## Не выполнено из-за недоступности API

- Две независимые учётные записи: чтение и изменение чужого продукта/draft/profile/settings.
- Повторная и параллельная регистрация одного e-mail.
- Одновременные `use`, `discard`, `approve` и `reject` для одного ресурса.
- Ответы обработчиков на пустые, сверхбольшие и типово неверные payload'ы.
- Реальные миграции PostgreSQL, cookie-session lifecycle и CORS.

## Условия для повторного запуска

1. Предоставить Go 1.25, требуемый проектом.
2. Предоставить Docker или совместимый контейнерный runtime.
3. Выполнить `make up`, убедиться в ответе `GET /healthz` со статусом 200.
4. Повторить все 12 сценариев; для сценариев ownership и concurrency использовать
   две сессии, реально созданные ресурсы и параллельные запросы.
