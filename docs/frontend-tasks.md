# Backlog Front-End MVP

**Агент:** Senior Project Manager — Frontend  
**Источники:** `shared/docs/product-description.md`, `shared/docs/product-context.md`, `frontend/docs/design-requirements.md` (эквивалент указанного в запросе, но отсутствующего `docs/design-spec.md`).

## Правило процесса

Каждая задача выполняется в порядке: **Frontend Developer → QA Engineer → Senior Frontend Developer**. На каждом этапе команда сверяется с `frontend/docs/design-requirements.md`; расхождение с ним — дефект или повод обновить требования через PM. Для задачи допускаются не более двух кругов ревью: первичный и один повторный после единого пакета исправлений.

## Задача 1: Структура и вёрстка всех страниц

**Описание:** Создать каркас публичных и приватных страниц из Design Requirements: вход, регистрация, продукты, добавление, фото-черновик, детали продукта, рецепты, настройки и 404. Использовать семантические дизайн-токены, компоненты и экранные состояния из ТЗ, без подключения production API.

**Критерии готовности (Dev):**

- Все страницы и общие компоненты (`AppShell`, navigation, list, form, dialog, alert, toast, skeleton) существуют и используют токены из Design Requirements.
- Вёрстка содержит предусмотренные loading, empty, error и `research_required` области; ручная форма доступна независимо от фото.
- Тексты имеют ru/en ключи, а не захардкожены в нескольких компонентах.

**Критерии готовности (QA):**

- Проверить наличие и назначение всех экранов против разделов 2–4 Design Requirements.
- Проверить пустые экраны и переходы без API через test fixtures; визуально сверить 320px, 768px и 1440px.

**Критерии готовности (Senior):**

- Проверить декомпозицию на переиспользуемые компоненты, отсутствие дублирования токенов и соответствие code style.
- Проверить семантическую HTML-структуру, локализацию, отсутствие неоговорённых функций (push, покупки, семья, календарь).

**Зависимости:** Design Requirements утверждены; API не требуется.

## Задача 2: Роутинг, авторизация и защита маршрутов

**Описание:** Реализовать маршрутизацию, регистрацию, вход, выход и восстановление cookie-сессии. Защитить приватные экраны и обеспечить предсказуемое перенаправление на вход.

**Критерии готовности (Dev):**

- Подключены только подтверждённые auth-контракты BE-003: register, login, logout и session.
- Private routes недоступны без сессии; return path безопасен; raw token не хранится в `localStorage` и не попадает в URL/логи.
- Регистрация содержит выбор страны только после публикации согласованного country/profile API; до этого состояние явно обозначено как blocked, без выдуманного DTO.

**Критерии готовности (QA):**

- Проверить login/logout, неверные данные, сетевую ошибку, 401 и доступ к приватному URL без сессии.
- Проверить, что браузерный storage и URL не содержат сессионного токена.

**Критерии готовности (Senior):**

- Проверить безопасную работу cookie-сессии, guard архитектуру, mapping ошибок и отсутствие утечки приватного UI до ответа session endpoint.
- Проверить типизацию контрактов и соответствие Design Requirements для форм и focus management.

**Зависимости:** Задача 1; BE-003. Production-часть выбора страны заблокирована до country/profile API.

## Задача 3: Интеграция данных для инвентаря и рецептов (GET)

**Описание:** Подключить получение списка продуктов, деталей и доступных рецептов; показать ленту срочности, фильтры и статусы срока на основе server-side данных.

**Критерии готовности (Dev):**

- Список, карточка и статусы используют данные BE-004/BE-005; UI не рассчитывает юридический срок в браузере.
- До появления query API сортировка и фильтры выполняются client-side для полного списка; `use by` со статусом `expired` не получает рецепт.
- Для `attention` и `research_required` показаны соответствующие текст, иконка и alert из Design Requirements.

**Критерии готовности (QA):**

- Проверить loaded/empty/filtered-empty/error состояния, поиск, фильтры, 403/404 и отсутствие утечки чужих данных в UI.
- Проверить, что `expired use by` не участвует в рецептах, а `best before` после даты показывает предупреждение.

**Критерии готовности (Senior):**

- Проверить cache/revalidation, обработку неизвестного статуса и производительность списков без избыточных запросов.
- Проверить типобезопасность DTO, разделение data layer и presentation, соответствие ленте срочности из Design Requirements.

**Зависимости:** Задачи 1–2; BE-004, BE-005. Рецепты блокируются до публикации HTTP-контракта BE-005.

## Задача 4: Формы и операции изменения данных (POST)

**Описание:** Реализовать ручное создание продукта, подтверждение «использован»/«выброшен» и клиентскую/серверную валидацию. Добавить редактирование только при появлении отдельного account-scoped API; в текущем scope его нет.

**Критерии готовности (Dev):**

- Форма требует название, тип даты и дату; optional поля соответствуют Design Requirements и BE-004.
- Submit, use и discard блокируют повторный клик, показывают результат и корректно обновляют список/карточку.
- Ошибки API отображаются у поля или на уровне формы, не теряя введённые значения; минимальный e-mail порог 60 минут учитывается только после согласования settings API.

**Критерии готовности (QA):**

- Проверить обязательные поля, неверный тип даты, API validation error, success, повторный submit и terminal action.
- Проверить, что destructive-действие требует подтверждения и что терминальный продукт не получает повторный lifecycle action.

**Критерии готовности (Senior):**

- Проверить разделение form state и API state, идемпотентность UI, отсутствие optimistic-рассинхронизации и соответствие контрасту/focus из ТЗ.
- Проверить, что UI не добавляет неподтверждённые PATCH/PUT endpoints.

**Зависимости:** Задачи 1–3; BE-004. Settings API и product edit не входят до отдельного backend-контракта.

## Задача 5: Фото-черновик и безопасность недоверенных данных

**Описание:** Реализовать загрузку фото, этапы распознавания и проверку черновика с явными approve/reject. Ошибка распознавания не блокирует ручной путь.

**Критерии готовности (Dev):**

- Photo upload показывает этапы `uploading`/`recognizing`; DraftReviewForm делает поля редактируемыми.
- Только успешный `approve` создаёт продукт; `reject`, timeout и ошибка не создают его и ведут к безопасному fallback.
- OCR/LLM-значения выводятся только plain text: HTML/URL не становятся исполняемым кодом, ссылкой или изображением автоматически.

**Критерии готовности (QA):**

- Проверить success, неполный draft, отказ в camera permission, timeout, reject, double-click approve и 403/404 draft.
- Проверить fixture с HTML/URL-подобным текстом: скрипт не выполняется, приватное содержимое не раскрывается.

**Критерии готовности (Senior):**

- Проверить безопасную обработку файлов и недоверенного текста, cancel/abort cleanup, mutation invalidation и отсутствие двойного создания продукта.
- Проверить соответствие approve/reject flow, focus и error states Design Requirements.

**Зависимости:** Задачи 1–4; BE-006.

## Задача 6: Сквозные UI-состояния, адаптивность и доступность

**Описание:** Довести все экраны до единого поведения при загрузке, ошибке и отсутствии данных; обеспечить адаптив на 320px, 768px и 1440px и keyboard/screen-reader доступность.

**Критерии готовности (Dev):**

- Реализованы Skeleton, InlineAlert, Toast, EmptyState и retry по правилам раздела 8 Design Requirements.
- Нет горизонтального overflow; touch target не меньше 44×44px; `prefers-reduced-motion` учитывается.
- Реализованы skip-link, видимый focus, semantic landmarks, labels, dialog focus trap и ARIA-состояния.

**Критерии готовности (QA):**

- Проверить каждое loading/error/empty/blocked состояние на всех ключевых экранах и трёх viewport.
- Пройти keyboard flow: Tab, Enter/Space, Escape, focus return; проверить доступные имена controls и текстовые статусы.

**Критерии готовности (Senior):**

- Проверить WCAG AA-контраст, корректность ARIA без избыточных ролей, responsive-архитектуру и отсутствие CSS-специфичности, ломающей states.
- Проверить, что дизайн-токены и breakpoint-правила не дублируются по компонентам.

**Зависимости:** Задачи 1–5.

## Задача 7: Интеграционное тестирование и багфиксинг

**Описание:** Выполнить финальную интеграционную приёмку MVP, исправить один согласованный пакет дефектов и провести повторную проверку. Playwright является обязательным инструментом для визуала, адаптивов и пустых состояний.

**Критерии готовности (Dev):**

- Исправлены подтверждённые дефекты без расширения MVP; добавлены regression tests для каждого исправленного поведения.
- Playwright visual regression настроен в Chromium: `toHaveScreenshot`, baseline в `frontend/tests/visual/*.spec.ts-snapshots/`, `maxDiffPixelRatio ≤ 0.01`.

**Критерии готовности (QA):**

- Пройдены e2e сценарии: сессия, ручной продукт, lifecycle, фото approve/reject, сроки, пустые/ошибочные состояния и рецепты при доступном API.
- Сняты Playwright screenshots/traces для дефектов; проверены 320px, 768px, 1440px, без overflow и с доступной CTA.

**Критерии готовности (Senior):**

- Проверить итоговый diff, архитектурные регрессии, bundle/performance риски, security findings, тестовое покрытие и code style.
- Принять задачу либо вернуть единый пакет замечаний; новый блокер после повторной проверки эскалировать PM, не запускать третий круг ревью.

**Зависимости:** Задачи 1–6; все опубликованные backend API. Необходимо закрыть country/profile и recipes/settings blocker либо явно исключить зависимые flows из приёмки.
