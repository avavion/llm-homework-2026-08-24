## Условия для реализации

1. В production-клиент не добавлять выдуманные request/response поля: точные DTO и коды ошибок сверить с BE-003—BE-006 перед подключением.
2. Если контракт backend не готов к началу задачи, Senior Frontend Developer помечает задачу `blocked`, а не меняет требования или создаёт несогласованный API.
3. Повторное ревью разрешено только после единого пакета исправлений; новый блокер передаётся PM.

## Замечания первого круга

1. В FE-001 отсутствовали страна, группа регулятора и безопасный режим `research_required`.
2. В FE-003 не был определён владелец сортировки и фильтров при отсутствии query-параметров в BE-004.
3. FE-004 обещала редактирование без `PATCH`/`PUT` в контракте BE-004.
4. FE-006 не имела опубликованного HTTP-контракта recipes/settings.
5. FE-007 не определяла воспроизводимый visual-regression baseline и XSS-сценарий для OCR/LLM-полей.
6. Реестр ошибочно требовал ровно два, а не максимум два круга ревью.

Все замечания переданы одним пакетом для повторного круга; результат второго круга дополняется ниже.

## Результат второго круга

Первый пакет исправлений принят. Обнаружен один новый внешний блокер, который не устраняется Front-End изменением: BE-003 не публикует `country_code` в регистрации, хранение страны/группы регулятора или profile API. Поскольку выбор страны обязателен в `shared/docs/product-description.md`, реализация FE-002 без согласованного backend-контракта означала бы выдумать API.

**Вердикт:** `blocked`, эскалировано Senior Project Manager. Лимит двух кругов исчерпан; дальнейшее взаимное ревью не запускается до решения владельца и обновления backend-контракта.
