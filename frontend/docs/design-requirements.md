# Design Requirements Document — Front-End MVP

- **Продукт:** помощник по использованию продуктов до истечения срока годности
- **Версия:** 1.0 · **Дата:** 26.08.2026
- **Владелец:** Senior UI/UX Designer
- **Источники:** [описание продукта](../../shared/docs/product-description.md), [контекст продукта](../../shared/docs/product-context.md), [анализ конкурентов](competitor-analysis.md), [техническое ревью](reviews/2026-08-26-frontend-technical-review.md)

## 1. Введение

### Цель документа

Документ задаёт единые, проверяемые требования к web-интерфейсу MVP для дизайнеров, разработчиков и QA. Он описывает поведение, состояния, семантику и адаптивность; визуальные макеты не являются частью этого документа.

### Обзор продукта

Приложение помогает одному домашнему пользователю учитывать продукты, видеть, что нужно использовать первым, и получать e-mail-напоминания. Основная работа экрана — за несколько секунд ответить на вопросы «что есть», «что использовать первым» и «что сделать сейчас».

Ключевое правило безопасности: интерфейс не определяет пригодность еды. Он отображает подтверждённый сервером тип даты, дату и статус.

| Тип даты | После даты | UI-правило |
| --- | --- | --- |
| `use by` / «годен до» | `expired` | Красный статус «Срок истёк»; рецепт недоступен. |
| `best before` / «лучше употребить до» | `attention` | Янтарный статус «Требует внимания»; продукт и рецепт доступны с предупреждением. |
| `research_required` для страны | Нет автоматического решения | Информационное состояние «Правило уточняется»; нет юридического/медицинского вывода и обещания автоматического напоминания. |

### Границы MVP

**Входит:** e-mail/password, ru/en, страна и группа регулятора, ручное добавление, проверяемый фото-черновик, инвентарь, статусы, «использован»/«выброшен», e-mail-порог и простые собственные рецепты.

**Не входит:** native app, push, штрихкод, общий домохозяйственный список, покупки, календарь питания, внешние или LLM-рецепты, реклама и доставка.

### Дизайн-направление

Интерфейс — спокойный и data-first, а не «умная кухня» с множеством разделов. Природный зелёный используется для направляющих и подтверждающих действий, янтарный и красный — только для семантики срока. Отличительный элемент продукта — **лента срочности**: компактный блок «использовать первым», упорядоченный по реальному действию пользователя, а не декоративный календарь. Вокруг него интерфейс остаётся сдержанным: белые поверхности, ясные строки списка, текстовые даты и минимум иллюстраций.

## 2. Пользовательские сценарии (User Flows)

| ID | Сценарий | Шаги | Успех |
| --- | --- | --- | --- |
| UF-01 | Регистрация и вход | 1) Открыть регистрацию. 2) Ввести e-mail, пароль, язык и страну. 3) Отправить форму. 4) При успехе открыть «Мои продукты». 5) При следующем визите восстановить cookie-сессию. | Пользователь входит в свой инвентарь; токен не показывается и не хранится в browser storage. |
| UF-02 | Первый пустой инвентарь | 1) После входа увидеть пустое состояние. 2) Прочитать, зачем добавить продукт. 3) Нажать «Добавить продукт». | Открыта ручная форма; камера не требуется. |
| UF-03 | Ручное добавление | 1) Ввести название. 2) Выбрать тип даты. 3) Указать дату. 4) При необходимости заполнить количество, единицу, группу и место. 5) Сохранить. | Созданный продукт появляется в списке ровно один раз. |
| UF-04 | Добавление из фото | 1) Открыть ручную форму. 2) Нажать «Заполнить по фото». 3) Загрузить фото/дать доступ к камере. 4) Дождаться черновика. 5) Проверить и исправить поля. 6) Явно выбрать «Сохранить после проверки» или «Отклонить». | До `approve` продукта нет в инвентаре; reject/ошибка оставляют ручной путь доступным. |
| UF-05 | Использовать продукт первым | 1) Открыть ленту срочности или список. 2) Увидеть тип даты, абсолютную и относительную дату. 3) Открыть карточку. 4) Отметить «Использован» или «Выброшен». 5) Подтвердить действие. | Статус и список обновлены; повторный клик не создаёт дублирующее действие. |
| UF-06 | Разобрать дату | 1) В карточке/форме увидеть «годен до» либо «лучше употребить до». 2) Открыть короткое пояснение. 3) После даты увидеть соответствующее предупреждение. | Пользователь видит, что `expired` исключён из рецептов, а `attention` требует проверки. |
| UF-07 | Найти рецепт | 1) Открыть «Рецепты». 2) Увидеть доступные карточки. 3) Прочитать «Использует [продукт] — [срок]». 4) Открыть рецепт. | Нет рецепта, основанного на просроченном `use by`; для `best before` после даты показано предупреждение. |
| UF-08 | Настроить напоминания и страну | 1) Открыть «Настройки». 2) Изменить страну/язык. 3) Выбрать e-mail-порог не менее 60 минут. 4) Сохранить. | UI показывает серверное подтверждение или доступную ошибку; режим `research_required` не маскируется под безопасный статус. |

### Схема переходов

```text
Public:  Вход ←→ Регистрация ──успех──> Мои продукты
                                      ├──> Добавить вручную ──save──> Мои продукты
                                      ├──> Добавить по фото ──draft──> Проверить ──approve──> Мои продукты
                                      │                                  └─reject/error─> Ручная форма
                                      ├──> Карточка продукта ──used/discarded──> Мои продукты
                                      ├──> Рецепты
                                      └──> Настройки
```

### Навигация

- Desktop/tablet: `Продукты`, `Рецепты`, `Настройки` в боковой или верхней навигации; активный раздел имеет текстовый и визуальный индикатор.
- Mobile: фиксированная нижняя навигация с тремя разделами; CTA добавления остаётся отдельной текстовой кнопкой или FAB с доступным именем.
- Публичные экраны не показывают приватную навигацию. Защищённый маршрут при 401 ведёт к `/login` с сохранением безопасного return path.

## 4. Компонентная спецификация

### Общие правила

- Все интерактивные элементы имеют видимый `:focus-visible`, доступное имя и состояние disabled во время необратимого запроса.
- Не полагаться на hover: то же действие доступно касанием, клавиатурой и в контекстном меню.
- Никакой HTML из OCR/LLM не рендерится через небезопасный HTML API; текст выводится экранированным.

## 5. Дизайн-токены

### Цвета

Токены именуются по роли, а не по конкретному компоненту. Светлая тема обязательна. Тёмная тема не входит в MVP; до отдельной задачи нельзя инвертировать цвета локально в компонентах.

| Токен | Светлая тема | Назначение |
| --- | --- | --- |
| `--color-brand-700` | `#166534` | primary action, активная навигация |
| `--color-brand-600` | `#218B4C` | hover/focus accent, positive affordance |
| `--color-brand-100` | `#DCFCE7` | спокойный успех/фон активного статуса |
| `--color-canvas` | `#F8FAF7` | фон приложения |
| `--color-surface` | `#FFFFFF` | карточка, форма, dialog |
| `--color-text` | `#17211A` | основной текст |
| `--color-text-muted` | `#647067` | подписи и метаданные |
| `--color-border` | `#DDE5DC` | границы и разделители |
| `--color-info` / `--color-info-bg` | `#1D4ED8` / `#EFF6FF` | черновик, `research_required`, информационное сообщение |
| `--color-warning` / `--color-warning-bg` | `#B45309` / `#FFF7E6` | `attention`, quality warning |
| `--color-danger` / `--color-danger-bg` | `#B42318` / `#FEF0EE` | `expired`, destructive action |
| `--color-focus` | `#1D4ED8` | обводка клавиатурного focus; не заменяется цветом статуса |

**Контраст:** обычный текст и текст в контролах — не ниже 4.5:1; крупный текст — 3:1; focus indicator — не ниже 3:1 относительно соседнего фона. Статус всегда содержит текст и иконку.

Запасной system stack обязан поддерживать кириллицу: `system-ui, -apple-system, "Segoe UI", sans-serif`. Не использовать текст меньше 12px.

| Токен | Значение | Применение |

| `--space-1…8` | 4, 8, 12, 16, 20, 24, 32, 40px | Только кратные 4px внутренние/внешние интервалы |

## 6. Адаптивность

| Breakpoint | Layout | Навигация | Инвентарь и формы |
| --- | --- | --- | --- |
| `< 640px` | 4 колонки, 16px поля | Нижняя навигация; CTA добавления не перекрывается safe area | Одна колонка; фильтры в bottom sheet; строки минимум в 2 строки; dialog становится bottom sheet |
| `640–1023px` | 8 колонок, 24px поля | Верхняя компактная навигация | Лента срочности над списком; фильтры в popover; форма максимум 640px |
| `≥ 1024px` | 12 колонок, max 1200px | Боковая навигация 240px | Список 8 колонок + правая лента срочности 4 колонки; форма максимум 720px |

- Контент не имеет горизонтальной прокрутки при 320px, 768px и 1440px.
- Минимальная touch target для иконки/кнопки — 44×44px.
- Таблицы данных не переносятся как уменьшенный desktop: на mobile поля списка объединяются в логическую строку/карточку.
- Motion только функциональный: transition 150–200ms для раскрытия и подтверждения; `prefers-reduced-motion: reduce` отключает движение и оставляет мгновенное изменение состояния.

## 7. Доступность

### Семантическая разметка

| Область | Требование |
| --- | --- |
| Каркас | `<header>`, `<nav aria-label>`, `<main id="main-content">`, `<footer>`; skip-link ведёт к main. |
| Заголовки | Один `<h1>` на страницу; уровни без пропусков. |
| Продукты | `<ul>`/`<li>` для списка, или корректная `<table>` только при табличном desktop-представлении с mobile-альтернативой. |
| Форма | Нативные `<label for>`, `<input>`, `<select>`, `<button>`; required не заменяет текстовую ошибку. |
| Dialog | Нативный `<dialog>` либо `role="dialog"`, `aria-modal="true"`, подписанный `aria-labelledby`, фокус удерживается внутри. |
| Статусы | `role="status"` для неразрушающих уведомлений; `role="alert"` для blocking form error. |

### ARIA и доступные имена

- Icon-only кнопка имеет `aria-label`, например `aria-label="Открыть действия для молока"`.
- Скрываемый раздел использует `aria-expanded` и `aria-controls`.
- Поле с ошибкой имеет `aria-invalid="true"` и `aria-describedby`, указывающий на текст ошибки.
- Асинхронный список получает `aria-busy="true"` только на время запроса.
- Не использовать ARIA-роль, когда существует нативный элемент с тем же поведением.

### Клавиатурная навигация

1. `Tab` следует видимому порядку чтения; нет ловушек фокуса вне открытого dialog.
2. `Enter`/`Space` активируют кнопки; `Escape` закрывает dialog, popover и sheet без потери данных формы.
3. При открытии dialog фокус переходит на заголовок или первую безопасную CTA; при закрытии возвращается в вызвавший control.
4. После успешного создания фокус переводится на заголовок списка и screen reader получает подтверждение через live region.
5. После серверной ошибки фокус идёт на summary ошибки или первое ошибочное поле.

## 8. Обработка состояний

### Загрузка

| Контекст | Поведение |
| --- | --- |
| Список/рецепты | Skeleton повторяет будущие размеры карточек/строк; не показывать spinner вместо всей страницы. |
| Первичная сессия | Нейтральный полноэкранный progress с текстом «Проверяем вход…»; не показывать приватные данные до ответа. |
| Submit/approve/lifecycle | CTA disabled, текст действия в progress state и `aria-busy`; повторное нажатие невозможно. |
| Фото | Процент/этап, если доступен; иначе нескрываемый статус «Загружаем» → «Распознаём». |

### Ошибки

| Ситуация | Представление | Следующее действие |
| --- | --- | --- |
| Ошибка поля | Текст под полем + `aria-describedby` | Исправить поле |
| Duplicate e-mail / invalid credentials | Form-level alert без раскрытия серверных деталей | Проверить данные |
| Сеть/5xx | InlineAlert в области контента + «Повторить» | Повторить запрос; форма/черновик не теряются |
| 401 | Перенаправление на вход + нейтральное объяснение | Войти снова |
| 403/404 приватного объекта | Одна нейтральная страница «Не удалось открыть»; без имени/полей объекта | Вернуться к списку |
| Ошибка OCR/LLM | Alert возле фото + «Ввести вручную» | Продолжить без фото |
| Ошибка country/profile или recipes/settings API | Info/blocked-state для команды в development; в production — доступное нейтральное сообщение и fallback, определённый владельцем API | Не выдумывать локальные данные |

### Пустые состояния

| Экран | Текстовый принцип | CTA |
| --- | --- | --- |
| Инвентарь | «Здесь появятся продукты, которые вы добавите.» | «Добавить продукт» |
| Поиск/фильтры | «По этим условиям продуктов нет.» | «Сбросить фильтры» |

| Фото-черновик отклонён | «Черновик не сохранён.» | «Добавить вручную» |

## 9. Интеграция с API

### Принципы

- UI отображает server-side истину для авторизации, статуса срока, recipe eligibility и сохранения; не воспроизводит правила срока в браузере.
- Любой async запрос имеет loading, success и error UI из раздела 8.
- DTO, методы и коды ошибок подключаются только после подтверждения backend. Не добавлять поля/endpoint «для удобства UI».
- При работе с cookie-сессией запросы выполняются с согласованными credentials; frontend не читает и не сохраняет raw session token.

### Контрактная карта UI

| UI-область | Ожидаемый backend-контракт | До запроса | Успех | Ошибка / ограничение |
| --- | --- | --- | --- | --- |
| Регистрация, вход, выход, сессия | BE-003: auth endpoints и cookie | Form/submitting state | Redirect/обновление shell | Field/form error; 401 ведёт к login |
| Страна, группа регулятора, профиль | **Не опубликован: blocker** | Не подменять данными в production | Показать сохранённую страну/группу | FE-002 blocked до согласования `country_code`, `regulator_group`, profile read/update |
| Список/карточка/lifecycle продуктов | BE-004: create/read/use/discard | Skeleton/disabled lifecycle CTA | Обновить строку/детали, toast | 404/403 без утечки; ошибки рядом с контекстом |
| Сортировка и фильтры | Пока `GET /v1/products` без query contract | Список loading | Client-side sort/filter полного списка | Не считать локальные фильтры серверным поиском; query API требует отдельного согласования |
| Фото-черновик | BE-006: recognize/approve/reject | Upload/recognition progress | Только approve создаёт продукт; reject не создаёт | Fallback на ручную форму; не показать приватный draft при 403/404 |
| Рецепты и e-mail-настройки | **HTTP-контракт не опубликован: blocker** | Skeleton/form state только после согласования API | Карточки/подтверждение настройки | FE-006 blocked до endpoint, DTO, ownership и error model; fixture не заменяет production API |

### API-state checklist для разработчика

- [ ] Каждый endpoint имеет typed request/response, error mapping и тест на loading/success/error.
- [ ] `use by` после срока не получает рецепт даже при устаревшем client cache; после mutation cache invalidated/revalidated.
- [ ] `approve` идемпотентно защищён от двойного нажатия UI и обрабатывает server conflict без двойного элемента списка.
- [ ] Незнакомое поле статуса отображается безопасно как «Статус обновляется», логируется для диагностики и не получает danger-вывод.
- [ ] OCR/LLM строки отображаются как plain text; URL и HTML не становятся активным контентом автоматически.
